# Vanex S3 开机用户关联与对话存档

## 设计边界

- 设备身份 `cabGuid/IMEI/MAC`、业务用户 `userGUID`、角色 `RoleID`、智能体 `agentId` 分开管理。
- 每次上电生成新的 `bootID`。设备等待本次用户关联，不自动沿用上次使用人的身份。
- 后台根据已登录账号的设备权限签发绑定凭证，只有哈希存库。凭证默认有效期 24 小时，换人或解绑立即在服务端撤销；设备还必须校验本次开机 ID 和递增版本。
- 当前连接的用户、使用会话、用户资料快照保持不变。换人关闭旧语音连接，重新校验后开启新连接。
- 同一个智能体可以服务多台设备，但个人上下文与记忆按智能体和用户区分。不同用户不共享个人记忆；同一个用户可在后续使用中继续自己的记忆（取决于所选记忆服务）。
- 后台保存用户识别文本、AI 已生成文本和工具记录，默认不保存原始录音。AI 文本在进入语音合成队列前保存，`generated` 仅表示已生成，不代表设备已播放。
- 旧固件保留设备级服务，但未经签发验证的 `userGUID` 不再用于调取个人记忆。完整流程需要新固件与新后台配套。

## 实际操作

设备 MAC 与业务用户并非永久一对一绑定：同一设备可以先后分配给不同 userGUID，同一 userGUID 也可以换用同一管理账号下的另一台设备。每台设备同一时刻只有一个有效使用会话；换人撤销本设备旧会话，不修改其他设备的会话。画像按管理账号与 userGUID 保存，历史记录继续归属原用户和原会话。

1. 在智控台设备管理中进入“用户关联”页面，选择设备的 MAC 地址。
2. 从客户系统 `topic/{imei}/online` 收到的本次上线 JSON 中取得 `cabGuid` 和 `bootID`，粘贴到页面；不要使用旧启动记录。
3. 输入本次使用人的 `userGUID`，填写昵称、语言、兴趣、讲解风格并保存。
4. 创建关联，复制后台生成的 `bindUser` 命令，通过客户现有 MQTT 系统发布到 `topic/{imei}/cmd`（`{imei}` 等于 `cabGuid`）。
5. 以设备后续上报的 `bindingState=ready` 为可对话确认。单纯创建成功、命令复制成功或者 MQTT 发出成功，都不等于设备已完成验证。
6. 按对话键开始交流。后台按用户和使用会话查询记录。更换用户时重新创建关联；结束使用时执行解绑，并发布后台返回的 `unbindUser` 命令。

上述手动流程保留作为备用。新增自动流程由独立的 MQTT 桥接服务接收客户原有的 `groupID + userGUID` 指令，在已登记的设备 MAC/cabGuid 映射和本次开机报文校验通过后，签发并下发完整绑定命令，页面自动更新设备报文。部署与验收见 `../mqtt-binding-bridge/README.md`。客户仍需在每次开机后明确分配本次使用人；设备自身不会凭空识别使用人。

## 换人专项验证（2026-10-07）

现有服务器已支持动态换人，本次未替换业务程序、重启服务或更改 OTA 发布。
新增 `smoke_user_switch.py`，通过公网 HTTPS 接口和真实数据库、独立测试账号及两台测试设备验证：

- 页面使用的签发接口加载用户 A 的画像。
- 同一用户 A 在另一台设备使用，画像一致，凭证与会话按设备隔离。
- MQTT 桥接使用的接口将原设备从 A 切换至 B，撤销 A 的旧凭证，不影响另一台设备。
- A 的延迟上报仍进入 A 的原会话，B 的记录与 A 分开；使用 B 查询 A 的会话被拒绝。
- B 切换回 A 建立新会话，旧的 B 请求重试被拒绝，历史记录保留。
- 解绑不删除用户画像或历史记录，也不影响另一台设备上的有效会话。

57 项桥接测试（含新增 A→B→A 确认流程）、15 项固件绑定源码检查和 13 项语音服务绑定测试通过。桥接完整测试使用断网隔离容器，真实接口测试不发布 MQTT、不调用模型生成对话。线上桥接源码与受测版本一致；全部测试数据已清理，真实设备身份、绑定状态和 API 程序保持不变。

这确认的是服务端功能和协议行为，仍需客户实机执行一次换人并观察匹配的 `bindingState=ready`，检查实际对话效果。页面编辑 userGUID 不会自动提交；手动路径仍需下发完整命令，自动路径则由客户 MQTT 分配指令触发。

## 接口

以下路由包含实际部署的 `/xiaozhi` 前缀，操作接口需要智控台登录凭证：

- `GET/PUT /xiaozhi/user/profile/{userGUID}`：用户资料。
- `GET/POST/DELETE /xiaozhi/device/{macAddress}/user-binding`：关联查询、签发、撤销。
- `GET /xiaozhi/user/profile/{userGUID}/sessions?page=1&limit=50`：使用会话。
- `GET /xiaozhi/user/profile/{userGUID}/sessions/{usageSessionID}/messages?page=1&limit=50`：会话记录。
- `POST /xiaozhi/config/user-binding/resolve`：仅可信语音服务器调用的凭证验证。
- `POST /xiaozhi/agent/chat-history/report`：仅可信语音服务器调用的幂等记录上报。

资料变更在下次创建关联时生效，不会静默改写正在使用的会话快照。绑定密钥只在创建响应中返回，请勿贴入公开日志或仓库。现场部署应使用 HTTPS/WSS 和受保护的 MQTT 通道，当前已有的公网明文 HTTP/WS 地址仍存在传输泄露风险。

## 容错与验证

- 上一轮开机的命令、较旧版本的命令、缺少签发凭证的用户 ID 均不得开启个人对话。
- 每次开始对话重新向后台验证；长连接每 15 秒复核。服务端撤销后最迟在下一次对话校验或后台巡检时拒绝旧连接。
- SQLite WAL 存放在持久挂载 `data/report-outbox.sqlite3`。HTTP 或数据库暂时故障时自动重试，同一 `messageId` 不重复落库。
- 断开连接不丢弃已入持久队列的记录，延迟补传仍归属原来的用户和使用会话。
- 存储写入失败时停止个人对话，不将未存档消息继续送去播放。重试耗尽的记录保留错误状态，需检查并重投，详见 `main/xiaozhi-server/docs/report-outbox.md`。
- 存档不同于摘要；摘要或标题生成失败不影响已经提交的原始文本。无录音、ASR 失败或设备未发送的数据不会被虚构为对话记录。

## 部署与回滚

本次部署目录：`/opt/xiaozhi-server/deploy-20261002-user-binding`。`backup` 中保留部署前数据库、API JAR、前端和 Python 源码及镜像标签。

Python 镜像基于现场镜像叠加修改。后续启动命令须包含覆盖文件：

```sh
cd /opt/xiaozhi-server
docker compose -f docker-compose_all.yml -f docker-compose.user-binding.yml up -d --no-deps xiaozhi-esp32-server
```

回滚应用时先停相关容器，恢复备份的 JAR/前端，并使用备份中记录的 Python 镜像。数据库迁移是新增表与可空字段，普通应用回滚不需要覆盖整库；整库恢复会覆盖部署后数据，须另行核对。

固件 OTA 使用应用镜像 `xiaozhi.bin`，不得将合并整包当 OTA 应用文件。上线时先用一台测试设备验证重启、换人、解绑、录音与回答，再扩大发布。

# OTA 版本错配排查与修复（2026-10-22）

## 已查实的问题

客户反馈刷回 2.1.6 后可以 OTA，怀疑新版未包含 OTA。服务器访问日志证明，
2.1.13-diag 在 11:49、12:02、12:28、12:39 等时刻向 `/xiaozhi/ota/` 发出了检查请求，
均获得 HTTP 200。HTTP 200 只表示请求获得响应，不代表设备已完成升级。

检查当时，公开发布记录 `1457bed80eff466491a26e9f35fcffdb` 的版本为 `2.1.15`，
实际文件仍为 `vanex-s3-2.1.13-diag-4273f51f4c92.bin`：

- BIN 内置版本：`2.1.13-diag`。
- 长度：3,236,640 字节。
- SHA-256：`4273f51f4c92ca0cb50d22d3a6705417fea9321c0bef8665d0367ef2215bfdee`。
- 发布记录在 12:27、12:39 有后台修改请求，排查时最后更新时间为 12:39:01。

把后台版本号写大并不会修改 BIN 内的程序或版本。这会使已安装 2.1.13-diag 的
设备继续收到同一个旧包，成功安装后仍为 2.1.13-diag，形成重复升级条件。
2.1.6 能升级到这个包，与上述现象并不矛盾。

另有一次服务器向客户端发送了 376,337 字节后结束连接，少于完整包长度。
这说明存在中断的下载，但仅凭服务端日志尚不能判定蜂窝网络、USB、设备重启或其他原因。
本次不把这一现象归因于版本错配，也不声称现场所有中断已消除。

## 本次处理

1. 备份发布记录后，将该条记录恢复为实际 BIN 版本 `2.1.13-diag`；未改动 BIN。
2. Vanex 固件新增、编辑接口在写入数据库前校验应用头、ESP32-S3 芯片标识、
   项目名、OTA 槽容量和内置版本。版本必须与 BIN 一致，长度以实际文件为准。
3. 对仅修改部分字段的请求，先读取原记录补齐类型、路径与版本，再进行校验。
4. 错误时接口返回明确消息，例如“版本号与 BIN 内置版本不一致：BIN 为
   2.1.13-diag。请填写该版本；发布新版需要重新编译并上传新的 BIN 文件”。
5. 校验范围为 `jiuchuan-s3` 和 `pilot-jiuchuan-s3`，其他板型和资源包保持原流程。

部署只替换 `OtaServiceImpl.class` 并新增 `FirmwareImageIdentity.class`。
现网其余 JAR 条目逐一校验保持一致，保留之前的诊断版本比较、鉴权及 Range 修复。
仅重启管理 API 容器，未重启语音容器、未发送设备强制重启或降级命令。

## 客户操作说明

- 当前真实最新版为 `2.1.13-diag`；已经安装该版时，不显示再次升级是预期行为。
- 有缓存连接配置的设备，通常在启动完成约 30 秒后、设备空闲时检查版本。
  版本检查运行在后台，检查时没有专门切换屏幕；下载阶段才显示升级状态。
- 新版程序保留 OTA。下一次升级应使用真正重新编译且版本更高的应用 BIN，
  不是只修改后台版本号或文件名。诊断版的 `-diag` 后缀也需要如实填写。
- OTA 上传应用 `xiaozhi.bin`；整机烧录合并文件用于烧录工具，不用于 OTA。
- 设备需已在智控台登记并启用自动更新；同一版本或更旧版本不会主动安装。
- 本次修复的是服务端发布流程，没有新增或发布新的固件版本。
  现场是否成功下载、写 Flash、重启，应以设备的新开机版本与完整串口日志验收。

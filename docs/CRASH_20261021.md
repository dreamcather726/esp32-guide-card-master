## 已确认的现场


PC 对应 `_xt_kernel_exc` 中的 `break 1, 0`，即进入内核异常入口后触发的调试异常。
`0x4037d84d` 是相邻异常处理代码的回溯地址，不应据此推断业务函数。
日志中的 `EXCCAUSE=1` 已被调试异常处理覆盖，不代表最初故障的原始异常号。
当前堆栈显示定时器中断通知任务、退出内核临界区的路径；没有足够现场判定最初的非法访问来源。
最后三行电量日志不证明电池故障；此现场也不证明 MP3 双重释放、服务器鉴权导致重启或 ISR 栈溢出。

## 已修正的代码隐患

- 音频启停增加串行化和幂等保护。停止时标记取消，清空队列，等待输入、输出、编解码三个工作任务完成资源访问。
- 任一任务创建失败会回收本次已启动任务。等待超过 5 秒时保留停止状态，旧任务结束之前拒绝重建，避免共享解码器被重复任务使用。
- 排队中的编解码生产者收到停止状态即返回，不再等待已经停止的消费者。
- 停止期间完成编码的录音测试包会被丢弃；测试队列容量查询与写入使用同一互斥锁。
- 解码器配置、关闭、打开、解码和输出重采样统一受同一互斥锁保护。重置不再与打开句柄并发。
- 重采样器打开失败不会假装已配置成功；切回原生采样率释放旧重采样器。
- 诊断任务列表使用结构化任务快照，避免 `vTaskList` 写入固定 1000 字节数组。原调用没有在这次崩溃路径出现，属于诊断代码防护。

以上是代码中确认的隐患修正，不等于已经确认本次内核异常的唯一根因。

## 定位版配置

版本为 `2.1.11-diag`，不作为全量 OTA 发布。保持 2.1.10 板型、Flash 参数、分区表和界面资源。

- ISR 栈 4096 字节、esp_timer 任务栈 6144 字节，增加诊断余量，不宣称原栈已证实溢出。
- 启用任务栈末端观察点、临界区使用检查和轻量堆越界检查。
- 开机输出固件版本、复位原因、ELF 校验值；周期记录内部堆完整性和任务栈余量。
- 崩溃通过 UART 输出 ELF core dump，不更改 Flash 分区布局。转储期间延迟重启是预期现象。

构建时使用独立配置：

```powershell
idf.py -B build_crash_diag '-DPROJECT_VER=2.1.11-diag' '-DSDKCONFIG=sdkconfig.crash_diag' '-DSDKCONFIG_DEFAULTS=sdkconfig;sdkconfig.diagnostics' build
```

这里 `sdkconfig` 应为经过核对的 2.1.10 板型配置，不能替换为其他板型默认配置。

## 验证与设备复测

新增主机测试抽取生产代码，在模拟 RTOS 上验证反复启停、重复启动、三个任务分别创建失败、工作任务卡住时禁止重复启动、队列饱和退出、解码/采样率更换/重置并发、资源创建失败恢复。
启用 AddressSanitizer 和 UndefinedBehaviorSanitizer；这些测试不模拟真实 ESP 中断、PSRAM、I2S 或射频环境。

```sh
python3 tests/run_audio_runtime_host_tests.py
```

设备复测先限一台，保留完整串口日志：上电、待机、按键对话、SD 的 MP3/WAV 切换、角色切换、灯阵列、网络中断与恢复、OTA 失败后继续对话。
记录 IMEI、版本、动作和发生时间。发生异常时保留从上电到 `CORE DUMP END` 及重启后的全部日志，不只截取寄存器区。
Core dump 可能含用户话语和运行时凭证，仅通过私密渠道交给排查人员。
本次没有实机复现结果，也没有向线上设备推送定位版。

## 后续日志与 2.1.12-diag

新日志设备运行 2.1.11-diag，没有出现新的 panic。配置失败对应服务器
`Integer.parseInt("11-diag")` 异常，已修复版本后缀兼容，并保持诊断版不进入全量发布。
设备同时增加配置响应校验，服务端错误或空配置不再视为成功；重试耗尽仍安排后台检查。

日志的内部堆最低约 603 字节，属于需要跟进的内存风险，不足以单独证明先前 BREAK 的根因。
2.1.12-diag 将唤醒词历史 PCM 明确放入 PSRAM，释放临时 AFE 配置，补上初始化失败检查。
保持原诊断配置与唤醒功能，实际内部堆改善量待设备日志确认。

新增电池电压日志使用同次校准 ADC 采样。发现 GPIO4 电池 ADC 曾被当作数字充电状态脚，
现改为无独立充电状态输入，滤波电量允许随实测电压双向更新；保留原电压曲线，等待万用表校准数据。
4G 继续上传原始 CSQ；GPS 仍只处理坐标/定位状态，卫星 C/N0 需模块提供相应报文。

## USB 异常现场与 2.1.13-diag

客户后续截图的 ELF 标识为 `25a93c817`，对应保留的 2.1.11-diag 符号文件；
它不能证明客户已经运行 2.1.12-diag。客户回复当前安装版本暂时不清楚。

截图先出现 RNDIS 写入失败、USB endpoint handle 无效、endpoint halt 失败、媒体连接状态查询失败，
随后为 CPU1 interrupt watchdog。按匹配 ELF 解析，CPU1 在 idle hook，CPU0 在
`systimer_hal_get_counter_value` 等待计数器有效、由 esp_timer 任务调用。
这只能确认异常现场和先后顺序，尚不足以证明 USB、系统时间未设置或鉴权 401 是重启根因。

2.1.13-diag 修正已确认的 USB 驱动隐患：

- RNDIS 初始化、设置、查询和 keepalive 检查响应类型、请求编号、状态及实际长度。
- 查询按协议规定的相对偏移复制；对目标容量、最短数据及整数边界进行校验。
- 控制传输容量包含 setup 包，使用完成传输的实际数据长度，短 IN 响应剩余部分清零。
- 超长数据退出时释放发送互斥锁；发送提交失败、取消和断开等结果归还发送令牌。
- 初始化命令缓冲区和发送包保留字段清零；命令提交失败即返回。
- 必需的 packet filter 配置失败仍返回错误；可选 multicast 配置被拒绝时记录警告。

新增 `tests/run_usb_transport_host_tests.py` 抽取生产例程进行故障注入，
以 ASan/UBSan 验证短包、越界偏移/长度、过期请求编号、失败状态、发送失败、锁与令牌释放。
包含 100,000 个响应变异输入，最终测试通过；现有 6 项 RNDIS 源码回归检查也通过。

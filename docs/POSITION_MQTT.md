# ML307C 定位接收与四角图标

`2.1.22` 首次包含定位接收、信号/电量/卫星/位置四角状态。`2.1.23` 增加[导览页面切换](GUIDE_PAGES.md)并修正信号显示，RGB 保持不变。

## 独立定位 MQTT

- Broker：`mqtt://iot.suji.work:1883`。
- 客户端 ID：`s3-position-<15位IMEI>`，与模组发布端和业务 WSS 客户端区分。
- 只订阅：`topic/<15位IMEI>/position`，IMEI 不带 `s3` 后缀。
- `2.1.24` 在原有开机资源流程结束后，由现有 MQTT 管理任务先检查定位连接，再申请业务 WSS 临时凭证。网络和有效设备身份就绪才登录；业务接口 403 的等待期间也继续维护定位连接。
- 此客户端仅接收，不发布定位，不使用通配符订阅其他设备。
- 断线自动重连并重新订阅；更换本次设备 IMEI 时停止旧客户端并切到新的 topic。

配置在 `main/boards/jiuchuan-s3/position_mqtt_config.h`；密码不放入版本库。复制相邻 `position_mqtt_local.h.example` 为 `position_mqtt_local.h`，填写本地密码，该文件已加入 `.gitignore`。当前工作区已按用户提供的密码配置本地文件。默认源码缺少本地密码时不发起定位 MQTT 登录，但仍更新信号图标，并在日志说明缺少配置。分享源码或在另一台电脑构建时需重新提供本地凭证文件。

2026-11-17 实连检查：用户更正密码后，服务器 MQTT CONNECT 与样例设备 topic 的 SUBACK 均已成功，验证账号登录和订阅权限可用。短时检查尚未收到该设备的定位 PUBLISH，持续接收仍需模组在线验证。本次未向服务器发布定位或控制消息。

## 消息字段

解析用户提供的 JSON 示例，同时接受数字和数字字符串；也兼容外层 `payload` 对象。

| 字段 | 用途 |
| --- | --- |
| `latitude` | 纬度，ML307C 的 `4003.829193` 转为约 `40.0638198833` 度 |
| `longitude` | 经度，`11625.225067` 转为约 `116.4204177833` 度；兼容旧 `longtitude` 拼写 |
| `fix` | `1` 为有效；兼容 2～5，且必须有有效非零坐标才显示定位已就绪 |
| `nsat` | 卫星数，0～99 的整数；缺失或非法显示 `--`，不把示例 `15`/`24` 写死 |
| `Scene` / `scene` | 右下角位置/景点编号；字符串保留前导零，缺失或为空显示 `--` |

原有十进制度数坐标在合法范围内继续接受。收到报文时卫星数和 Scene 代表当前快照，缺失字段不会沿用上条报文。示例没有 Scene，因此右下角显示 `--`，不会拿坐标、室内 ID 或讲解音频文件名冒充定位编号。

固定 topic 之外的消息、retained 定位、超过 4096 字节、错误分片顺序、非法 JSON 不更新位置。支持 ESP MQTT 将一条 JSON 拆成多次 DATA 回调。断开连接或 90 秒未收到有效报文时，清除旧卫星数和 Scene，恢复未定位状态。坐标不写到日志或 NVS。

2.1.46 的诊断页区分订阅拒绝 `POS MQTT SUB DENIED`、订阅后 60 秒未收到实时数据 `POS NO DATA #XXXXXX`、旧保留消息 `POS RETAINED WAIT` 和无效报文 `POS RX BAD PAYLOAD` / `POS RX BAD PACKET`。`XXXXXX` 是订阅主题所用 IMEI 的后六位，完整主题见串口 `[SUBSCRIBE]`。针对样例中连续出现的 `"Wifisan":,"Wifisan":[]`，解析会跳过第一个缺少值的字段，其余字段继续按原规则校验。

业务 WSS 客户端订阅 `topic/{imei}/position`，其中 `{imei}` 为模组 IMEI 拼接 `s3`。屏幕定位状态由上面的独立 ML307C 定位客户端更新。

## 四角状态

| 位置 | 显示及来源 |
| --- | --- |
| 左上 | 蜂窝信号四格，由现有 USB 网络任务通过 ML307 AT 口读取 `AT+CSQ` |
| 右上 | 电池外框和数字百分比，根据电池 ADC 电压，在 3.2 V（0%）和 3.7 V（100%）之间线性换算 |
| 左下 | 卫星图标与 `nsat`；有有效定位常亮，未定位时闪烁 |
| 右下 | 定位图标与 Scene 编号；过长编号省略显示 |

CSQ：1～7 一格、8～15 两格、16～27 三格、28～31 四格；0、99、读取失败或拔掉模块时隐藏信号图标。AT 口就绪后就开始读取，不等 IP、IMEI 或 MQTT。RNDIS 在线且 IMEI 已读取时，有效读数约 10 秒刷新，失败或未知约 5 秒重试；连接过程中沿用原网络任务的重试节奏。

四角占用上下各 20 像素；字幕位于中间，避免遮挡底部定位信息。二维码启动页覆盖这些状态，关闭后显示四角。`2.1.23` 的大时钟和页面行为见导览页面文档。

## 两路 MQTT 启动诊断

2.1.48 的 `CabinetMqtt` 和 `PositionMqtt` 默认连接 `mqtt://iot.suji.work:1883`。业务客户端使用 `<IMEI>s3` 作为 clientId，定位客户端使用 `s3-position-<IMEI>`。串口日志区分登录、连接成功、订阅成功、订阅拒绝和断线。

`[TASK_STARTED]` 仅代表任务启动，`[CONNECTED] ... CONNACK=0` 才代表服务器登录成功。`[ERROR]` 打印 error type、CONNACK、TLS 和 socket errno，可区分认证拒绝和连接错误。

`Error create mqtt task` 是 ESP MQTT 在 FreeRTOS 创建任务失败时打印的本地错误，尚未开始服务器登录。`2.1.23` 仍使用原任务创建方式，不能认定该版本已解决。此前的诊断修改保留两个客户端和原栈大小；启动及失败时补充 `internal_free`、`internal_largest` 和启动时 `psram_free`，并区分 `register_event`/`create_task` 失败。定位客户端初始化/任务失败后销毁句柄，现有循环继续重试。

内部 RAM 不足或碎片化是该报错的可能原因；PSRAM 剩余多不代表能分配普通 FreeRTOS 内部栈。需要实机日志判断，不通过盲目缩减栈或全局改变内存配置来宣称已修复。主机已模拟初始化、事件注册及任务启动失败，验证资源清理、重试恢复、错误阶段与密码隐藏；这不等同于复现真实 ESP32 内存耗尽。

## 2.1.24 减少内部任务栈占用

移除定位订阅器单独的 `position_mqtt` 管理任务（6144 字节内部栈），将其循环改为 `Poll()`，由原有 `cabinet_mqtt` 管理任务调用。两路 MQTT 仍是独立客户端，各自的协议栈任务不变；定位协议栈仍使用原 4096 字节栈，业务管理任务仍为原 12288 字节栈，不通过缩小栈回避问题。省去约 6KB 内部 RAM 及一个任务控制块，为第二路 MQTT 的任务创建留出空间。

管理任务每次循环先维护定位，在凭证重试等待中每约一秒检查一次，保留定位 MQTT 自动重连、IMEI 切换和定位超时清理。单次业务 HTTP 调用最长按现有 10 秒超时处理，调用期间定位协议栈独立运行，定位管理检查会相应延迟。关停时等管理任务退出再释放定位对象，避免仍有工作访问已释放对象。

主机测试运行生产管理任务的 `Start/Run/WaitOrStop`，模拟业务 403 重试、任务重复启动和关停。栈预算模型中，旧结构 `12288+6144+4096=22528` 字节超出 20000 字节预算时失败，新结构 `12288+4096=16384` 字节成功；这是对栈占用减少的确定性验证，不代表实测板上全部堆占用。仍需检查实机启动日志中的 `internal_largest` 与 `[CONNECTED]`，确认实际内存压力下两路均成功。

已使用 ESP-IDF 5.5.4 / GCC 14.2.0 编译并打包 `releases/esp32s3-jiuchuan-2.1.24/`。应用为 3,400,896 字节，分区剩余约 18%；ESP32-S3 镜像校验、16MB 完整镜像各分段核对及 SHA-256 清单通过。该版本包含诊断日志，未进行实机烧录。
